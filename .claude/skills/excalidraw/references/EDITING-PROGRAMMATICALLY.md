# Правка .excalidraw.md скриптом

Когда правок много и они механические (пересчитать числа на схеме, добавить десяток
подписей, разложить блок комментариев) — руками в Excalidraw это долго и легко ошибиться.
Здесь про то, как делать это скриптом и не сломать файл.

Инструменты — в `../scripts/`.

## Анатомия файла

```
---
frontmatter (excalidraw-plugin: parsed, tags: [excalidraw], ...)
---

==⚠ Switch to EXCALIDRAW VIEW...==

# Excalidraw Data

## Text Elements          ← ИСТОЧНИК ПРАВДЫ для текста элементов
Текст блока ^8charIdX

Другой текст ^8charIdY

## Embedded Files          ← картинки и LaTeX-формулы
85f1653d...989977983b5: $$\sum = 200$$

## Drawing
```compressed-json
<LZ-String base64, строки по 256 символов через пустую строку>
```
%%
```

Три вещи, которые ломают наивную правку:

1. **Сцена сжата.** Блок `compressed-json` — это `LZString.compressToBase64(JSON)`.
   Просто так его не прочитать; `scripts/lzstring.js` — тот же алгоритм на голом node.
2. **Текст живёт в двух местах.** При `excalidraw-plugin: parsed` содержимое текстовых
   элементов плагин берёт из секции `## Text Elements`, а не из JSON. Поменяешь только
   JSON — при открытии текст откатится. Менять надо оба (`excalidraw-io.js` делает это сам).
3. **Формат секции жёсткий.** Парсер плагина — `/\s\^(.{8})[\n]+/g`, дальше `pos += 12`.
   Отсюда: **id текстового элемента ровно 8 символов** и **ровно два перевода строки**
   после него. Элементы с более длинным id плагин молча переименует через nanoid.

## Порядок работы

```bash
S=".claude/skills/excalidraw/scripts"

# 1. посмотреть, что внутри: id блоков, координаты, куда ведут стрелки
node "$S/dump-scene.js" "Projects/.../Схема.excalidraw.md" | less
node "$S/dump-scene.js" "Projects/.../Схема.excalidraw.md" --tree   # только граф

# 2. написать разовый скрипт правки на excalidraw-io.js (см. ниже)

# 3. проверить, что новые блоки никуда не легли поверх
node "$S/check-overlap.js" "Projects/.../Схема.excalidraw.md" --color "#6741d9"

# 4. посмотреть глазами
node "$S/render-preview.js" "Projects/.../Схема.excalidraw.md" ".preview.png"
```

Разовый скрипт правки:

```js
const ex = require('.../scripts/excalidraw-io.js');
const doc = ex.load('C:/абсолютный/путь/Схема.excalidraw.md');

doc.setText('UuuTZTjl', '48,9%');                       // поменять существующий текст
doc.setLatex(null, '\\sum = 221');                      // LaTeX-узел
doc.labelArrow('arrowId', '11,3%');                     // подпись на стрелке
const c = doc.addText({                                 // комментарий
  text: 'первая строка\nвторая строка',
  x: -2600, y: -2400, fontSize: ex.FONT.S, color: ex.COLORS.violet,
});
doc.addArrow({ from: [-2295, -2248], to: [-1545, -2092], color: ex.COLORS.violet });

doc.save();
```

Разовый скрипт — именно разовый: он описывает конкретную схему и в скил не кладётся.
Переиспользуется только `excalidraw-io.js` и утилиты рядом.

## ⚠ Obsidian Linter портит схемы

В хранилище включены `lintOnFileChange: true` и `lintOnSave: true`, а
`.excalidraw.md` **не** в списке исключений. При любой внешней записи в файл Linter
проходится по нему и вставляет пустые строки внутрь многострочных текстовых элементов —
все подписи разъезжаются в двойной интервал, габариты блоков уезжают.

Проявляется это коварно: файл меняется через секунду-две после записи, уже после того,
как скрипт отрапортовал об успехе.

Как жить:

```bash
# проверить, что файл стабилен
md5sum "путь"; sleep 3; md5sum "путь"        # хеши должны совпасть
```

Если не совпали — писать при временно выключённом плагине и обязательно вернуть как было:

```bash
obsidian vault="ObsiNotes" eval code="(async()=>{await app.plugins.disablePlugin('obsidian-linter');})();'ok'"
# ... правки ...
obsidian vault="ObsiNotes" eval code="(async()=>{await app.plugins.enablePlugin('obsidian-linter');})();'ok'"
```

Настройки Linter при этом трогать не надо: `enablePlugin` перечитывает `data.json`.
Постоянное лечение — добавить в Linter → *Files to ignore* правило `\.excalidraw\.md$`;
это решение пользователя, молча менять его конфиг не надо.

Смежное: у самого плагина есть настройка `addDummyTextElement` — фиктивный первый элемент,
который линтер может безопасно испортить. Она не спасает от описанного выше.

## Мелочи, на которых легко споткнуться

| Что | Как |
| --- | --- |
| Кегли шрифта S / M / L / XL | 16 / 20 / 28 / 36 (`ex.FONT`) |
| Фиолетовый для комментариев | `#6741d9` (`ex.COLORS.violet`) |
| Ширина текста | ≈ `0.54 × fontSize` на символ, но плагин пересчитает точно при открытии — реальные блоки выходят ~на 15 % шире оценки |
| Высота текста | `строк × fontSize × 1.25` |
| `index` (fractional) | строки, сравниваются лексикографически; новый элемент — `максимальный + символ` |
| Удалённые элементы | остаются в JSON с `isDeleted: true` и отсутствуют в `## Text Elements` — это нормально |
| Привязка стрелок | у новых элементов проще оставить `startBinding/endBinding: null` и задать координаты; «живую» привязку удобнее доделать мышью |
| LaTeX-узлы | `fileId` — просто ключ в `## Embedded Files`, пересчитывать хеш не нужно, достаточно переписать формулу (и `customData.latex`) |
| Файл открыт в Obsidian | закрыть вкладку перед записью: `app.workspace.getLeavesOfType('excalidraw').forEach(l=>l.detach())`, иначе плагин перезапишет файл своей версией |
